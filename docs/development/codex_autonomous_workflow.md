# Codex による複数チケットの自律開発

親セッションが対象チケットを取りまとめ，各子セッションは 1 チケットの PR 作成まで担当する．[AGENTS.md](../../AGENTS.md)，[Jira 運用](codex_jira_operating_rules.md)，[ブランチ運用](branch-governance.md) と併せて使う．この文書は実行時の手順であり，自動起動するプログラムやモデル設定ファイルではない．

## 1. 親が開始時に確定すること

1. ユーザーの対象チケットと完了範囲を記録する．バージョン全体の委任と，一部チケットだけの委任を区別する．
2. Jira の接続を確認し，対象の本文・受け入れ条件・状態・親・関連リンクを取得する．依存先は着手判断に必要なものだけ追加取得する．完了済みチケットや既存 PR を重複実装しない．
3. `git status --short`，`git worktree list`，リモートブランチ，既存 PR を確認する．統合ブランチを fetch し，起点 SHA を固定する．存在する統合ブランチを作り直さない．
4. 変更候補ファイル，公開契約，テスト，生成物，実行環境を調べ，依存関係と並列可否を判断する．同じゲームエンジンという分類だけで判断しない．
5. 次の実行表を親が所有するローカルの作業記録へ保存し，短い方針をユーザーへ伝えて着手する．実行表は子が変更しない．再開できるよう絶対パスを記録する．

| Jira | 依存／待機条件 | worktree／ブランチ | 起点 SHA／PR base | 担当ファイル・契約 | モデル／推論／理由 | 排他リソース | 子 ID／状態／PR |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 対象 key | なし，または先行 PR | 絶対パス／専用名 | 固定 SHA／統合先 | 編集範囲 | 実際の設定値 | GPU・ポート等 | 待機→実行→検証→PR 作成済み，またはブロック |

PUYO-110 のような保守エピックや PUYO-147 のバグも，特定バージョン向けにまとめる場合は，親エピックを付け替えず対象の統合ブランチを明記する．今回の準備タスク PUYO-262 の統合先は `integration/puyo-228-v1-8-0` とする．

## 2. 作業場所と共有リソースの分離

親は子の起動前に，各チケット用の worktree を作成する．以下は起点と未使用のブランチ名・ディレクトリを確認した後の例である．既存 worktree を上書きしない．

```bash
git fetch origin
batch_base_sha=$(git rev-parse origin/integration/puyo-228-v1-8-0)
git worktree add -b PUYO-190/garbage-event-lifecycle ../puyo-PUYO-190 "$batch_base_sha"
```

子には worktree の絶対パスを渡す．子は開始時に `pwd`，`git branch --show-current`，`git status --short` を確認し，以降のコマンドにその作業ディレクトリを指定する．子セッションは自動的にファイルシステムが隔離されるとは限らない．

| 対象 | 所有者とルール |
| --- | --- |
| ファイル・index・commit・push | 子が自分の worktree とブランチだけを操作する．他の作業場所で checkout，reset，stash，clean をしない．push 先を明示する． |
| worktree の作成・削除，fetch，共有 Git 設定 | 親が直列実行する．子の実行中に対象 worktree を削除しない．全子終了と未保存変更の有無を確認してから後片付けする． |
| 依存ライブラリ・native build | 子ごとの仮想環境・build 出力を使う．共有環境への install や生成物の上書きは親へ調整を依頼する． |
| 学習・評価・GUI | 出力先・ログ・一時領域・ポートをチケットごとに分ける．GPU，大量 CPU，表示環境を排他的に使う処理は親が順番を割り当てる． |
| プロセス停止 | 自分が起動し記録した PID だけを対象とする．広範囲な `pkill` で他セッションを停止しない． |
| Jira・PR | 各子が自分のチケットと PR を更新する．親は全体記録と取りまとめを所有する． |
| 統合ブランチ・stack の設定 | 親だけが調整する．子から他ブランチの取り込み，PR の merge，rebase，stack 同期を実行しない．共有済み履歴の書換えにはユーザーの明示指示が必要． |

担当外ファイルの編集や共有 API の変更が必要になった子は，該当操作を止めて親へ必要な変更と理由を送る．親は競合する子を停止または待機させ，担当範囲を再割当してから続行する．連絡なしに他の変更を取り込まない．

## 3. 並列化と依存関係

- 異なる worktree でも，同じ API，状態遷移，schema，lockfile を変える場合は干渉し得る．変更範囲が重なる場合は原則直列にし，調査のみ先行できるかを判断する．
- 独立したチケットは同じ起点 SHA から開始できる．最大同時数は実行環境の上限から親の枠を引き，CPU/GPU/メモリの予算も考慮する．上限まで起動すること自体を目標にしない．
- 先行変更を必要とする子は，先行 PR の実装・検証が完了するまで待つ．親は先行 head SHA を固定し，その SHA から後続 worktree を作成する．後続 PR の base は先行ブランチとする．先行変更を後続の実績として重複計上しない．先行の受け入れ条件が未達なら，依存する実装も待機させる．
- `github/gh-stack` を使う一括委任では，この base の連鎖をブランチ運用の例外とする．stack の最下段は必ず指定の統合ブランチへ向ける．独立 PR のレビュー順による連鎖は実装上の依存と区別し，Jira に架空の Blocks を追加しない．stack を使わない依頼では統合ブランチを base とし，依存先の取り込みを待つ．

### PUYO-190 と PUYO-239 をまとめて依頼された場合

PUYO-190 は着弾済みおじゃまの visual event 再生，PUYO-239 は窒息後の連鎖解決と終端判定が対象である．両者とも GUI/event lifecycle に触れる可能性があるため，実装の並列化を初期状態では許可しない．親が実際の変更範囲を調べ，独立性を確認できた場合だけ並列へ切り替える．重なる場合は先行 PR と待機条件を明記する．例えば PUYO-190 の検証済み head から PUYO-239 を開始し，後者の PR base を前者へ向ける．これは運用例であり，この文書の整備だけで両チケットへ着手したことにはしない．

## 4. モデル・推論・文脈の選択

親は起動ツールで利用可能なモデルと対応する推論レベルを確認し，実際に渡した値と理由を実行表に残す．固定の最上位設定を全チケットへ適用しない．以下のモデル名は本セッションで利用可能だった候補であり，将来の環境では同じ役割の利用可能モデルを選び直す．

| 作業 | 選択の目安 | 推論 |
| --- | --- | --- |
| 限定的な文書・設定の修正 | 標準のコード作業向けモデル（例: `gpt-6-sol`） | `medium` |
| 通常の機能実装・原因が絞れた不具合 | 同上 | `medium`，状態遷移が複雑なら `high` |
| 複数層にまたがる不具合・設計判断・統合競合 | 高能力モデル（例: `gpt-6-astra`） | `high` |
| 難しい原因究明が残る場合 | 高能力モデルを維持し，必要な子だけ再評価 | `xhigh` は具体的な理由がある場合だけ |

PUYO-190 は標準モデル＋`high`，PUYO-239 は終端・攻撃・replay の整合性にまたがるため高能力モデル＋`high` を初期候補とする．チケットの更新と実装調査後に確定する．`low` や最小モデルを実装の既定値にしない．再現に失敗する，設計契約が食い違う，同じ修正を繰り返す場合は親が範囲と設定を見直す．

モデルを変更できない起動環境では設定済みと偽らず，継承されたモデルと制約を記録する．本セッションの `spawn_agent` ではモデル／推論の指定時に `fork_turns="none"` または限定した履歴を使い，全履歴の fork と混在させない．別の起動ツールではその実際の schema に従う．CLI の設定を流用してツールへ未知の引数を渡さない．

トークン削減は，親が全履歴を複製せず必要なチケット内容・契約・参照先だけを渡すことで狙う．子の結果は要約と証跡パスで返し，親が同じ調査をやり直さない．ログ全文や Sprint 全件の本文を通常の引継ぎに含めない．子は再委任しない．分割によって総トークンが増える場合もあるため，観測できる場合は利用量と重複調査を振り返る．

## 5. 子への委任テンプレート

以下を埋めて起動メッセージに含める．子が親の会話を読まなくても作業できる情報量にする．

```text
担当 Jira: <key / URL，本文の要点，状態，親，関係するリンク>
目的・受け入れ条件: <観測可能な条件，仕様上の制約>
worktree: <絶対パス>
branch / 起点 SHA / PR base: <確定した値>
編集範囲・共有契約: <所有するパス，変更前に親へ相談する境界>
依存関係: <先行 PR，開始条件，並列相手と干渉回避>
モデル / 推論: <実際の設定と理由>
参照先: <必要な設計・関連テスト・AGENTS.md のパス>
検証: <最低限の回帰・受け入れ確認，実行予算，排他リソース>
成果物・ログ: <チケット専用出力先>

指定 worktree の AGENTS.md と該当ディレクトリの追加指示を読み，
自分の Jira を着手時に In Progress にする．
調査，実装，必要な検証，対象ファイルだけの commit，明示した branch への
push，指定 base への PR 作成まで進める．PR は日本語の既定書式を使い，
reviewer は指定しない．merge，stack 操作，他の子の起動はしない．
担当外の変更・依存の判明・認証や実行上限の問題は親へ報告する．
担当 Jira のセッションコメントは 1 件にまとめ，PR と検証証跡を含める．
受け入れ条件を満たしたら COMPLETE へ遷移する．Done にはしない．
未達条件があれば未完了として返す．PR 作成だけで完了と扱わない．
```

子の最終報告は以下に絞る．

```text
Jira / 子 ID / 状態:
branch / 起点 SHA / head SHA / PR URL / base:
実施内容・変更ファイル:
検証コマンド・結果・証跡パス・未実施理由:
残課題・待機条件・他チケットへの影響:
Jira コメント ID と遷移結果:
```

子が停止した場合は，親がまずプロセス・ブランチ・未コミット差分・既存 PR・Jira コメントを確認する．二重起動せず，同じ担当を再開するか，停止を確認して所有者を交代する．親が代理更新するときは既存コメントを更新し，重複投稿を避ける．

## 6. 親による確認とレビューの取りまとめ

全子の報告を待つだけでなく，依存や担当範囲の変更を随時調整する．終了時は各 PR の base/head，差分，無関係な commit の混入，受け入れ条件と検証結果を確認する．テスト結果は head SHA に紐付け，後から変更した場合は影響する検証を更新する．単体の成功を組合せの成功として報告しない．

組合せ QA が必要なら，親が専用の一時 worktree とローカル検証用ブランチで，対象 PR の確定 SHA を順に取り込む．統合ブランチへ直接 push しない．競合は担当の子へ差し戻し，対象範囲の検証を再実行する．ローカル検証用の取り込みは PR の merge と区別する．

### gh-stack の確認と利用

使用する拡張は [github/gh-stack](https://github.com/github/gh-stack) である．2026-09-23 に v0.1.1 を導入し，help と同タグの実装を確認した．別環境では未導入の場合だけインストールし，バージョンと help を再確認する．

同日に `gh api repos/shhchan/puyo-ai-dev-platform/stacks` の読み取り成功（空配列）も確認した．書き込み権限と実際の stack 作成の成功は別途確認する．

```bash
gh extension list
gh extension install github/gh-stack  # 未導入の場合だけ
gh stack --version
gh stack link --help
```

本運用では，各子が既定書式の PR を作成し，親が既存 PR の URL を指定して `gh stack link` を実行する．このコマンドは PR の base を順番に合わせて変更するが，Git の履歴を積み直さない．親は先に履歴と差分を整える．単独 PR のときは stack を作成しない．

1. 全子の Git 操作とプロセスが停止し，未コミット変更がなく，PR が open（draft を含む）で auto-merge／merge queue に入っていないことを確認する．各 PR の現在の base/head SHA と stack 所属を記録する．
2. 依存する PR は先行 head が後続 head の祖先であることを `git merge-base --is-ancestor <先行 SHA> <後続 SHA>` で確認する．独立して並列開発した PR は，親が後続 worktree の所有権を引き継ぎ，直前の確定 head SHA を `git merge --no-edit <先行 SHA>` で取り込む．下から順に行い，履歴を書き換えず，対象 branch へ通常の push をする．子の作業中には行わない．
3. 競合した場合は stack の構築を保留し，担当の子を 1 件ずつ再開して解消・検証する．親と子で同じ worktree を同時操作しない．先行との差分にそのチケットの変更だけが残ることを確認し，更新された head で必要な回帰・組合せ QA を実施する．マージ済み履歴を含むこの運用では `gh stack modify` など線形履歴を前提とする操作を使わない．
4. 次のコマンドの URL を実際の PR に置き換え，下から順に指定する．`--base` は省略しない（省略すると repository default branch が選ばれる）．URL 指定により，branch 引数による自動 push／PR 自動作成を避ける．

```bash
gh stack link --base integration/puyo-228-v1-8-0 \
  https://github.com/shhchan/puyo-ai-dev-platform/pull/PR_NUMBER_A \
  https://github.com/shhchan/puyo-ai-dev-platform/pull/PR_NUMBER_B
```

5. 戻り値だけで成功と判断せず，各 PR を `gh pr view <URL> --json url,baseRefName,headRefName,headRefOid,body,reviewRequests,isDraft` で再取得する．最下段の base，後続の連鎖，head SHA，差分，本文，reviewer を確認し，stack の番号／リンクと構成を実際の GitHub 表示または API で確認する．既存の What / Why / QA / References と人間の追記を保持する．`link` は base 更新の失敗を warning として続行する場合があるため，warning を見落とさない．
6. PR の References に stack の順序と先行 PR を記載し，子の Jira コメントを必要に応じて更新する．`--open` は全対象の検証と draft 解除の判断後だけ使い，reviewer の指定は行わない．一覧をユーザーへ一括提示する．

`gh stack link` はローカル stack 管理情報を作らないため，直後の `gh stack view` を成功確認の前提にしない．`init`，`submit`，`sync`，`rebase`，`push` はこの取りまとめでは使わない．特に `sync` は rebase や force-with-lease を伴い得る．後から先行 PR を修正した場合も，下から通常の merge で伝播して差分・QA・head SHA を更新する．

API が未提供・権限不足などで失敗した場合は，エラーと部分適用された base の有無を確認して報告する．親が直前に変更した base だけを記録値へ戻すか，正しい連鎖を保って再実行するか判断し，人間の新しい変更を上書きしない．無関係な stack の変更・削除，無断の履歴書換えはしない．個別 PR とレビュー一覧は提示し，stack 未作成を明記する．GitHub 上の stack 作成そのものは，実際の複数 PR を対象にした時点で検証する．

| レビュー順 | Jira／PR | base／head SHA | 依存・取り込み順 | 検証結果 | 残課題 |
| --- | --- | --- | --- | --- | --- |
| 1 | リンク | 統合先／確定 SHA | 独立または先行 PR | 個別 QA／組合せ QA | なし，または具体的な条件 |

レビュー依頼はこの一覧をユーザーへ一括提示することで行う．merge・release や GitHub reviewer の指定は，別途明示された指示に従う．一部がブロックしている場合も，レビュー可能な PR と未完了チケットを区別して提示する．

